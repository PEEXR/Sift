## THIS DISPATCH = Stage 15: full in-app Backup & Restore (user feature)

Why: the app's data (OCR text, embeddings, collections, memberships, settings) lives only in the app's private storage (`android:allowBackup="false"`), so an uninstall/clear-data/new phone loses hours of indexing. Add a user-facing full backup to a file the user chooses (Storage Access Framework), and a restore that re-attaches it to the current library. The model files are NOT backed up (they re-download). Nothing is uploaded by the app.

### 1. Format (pure, JVM-tested) — new `data/backup/FullBackup.kt`
- Single JSON document (kotlinx.serialization), optionally GZIP-compressed on disk (write with `GZIPOutputStream`; detect on read by the gzip magic bytes 0x1F 0x8B so both plain and gzipped files restore). Suggested default file name `sift-backup-YYYY-MM-DD.json.gz`, MIME `application/gzip` for create (accept `application/gzip`, `application/json`, `*/*` on open).
- `FullBackup(version: Int = 1, createdAtEpochSec: Long, appVersion: String, settings: BackupSettings, collections: List<FullCollection>, screenshots: List<FullScreenshot>)`.
  - `BackupSettings(autoFillSensitivity: String, indexingQuality: String, autoIndexNewScreenshots: Boolean, measuredSecPerImageAt280: Double?)` (strings are enum names; unknown names fall back to defaults when restoring).
  - `FullCollection(key: String /* stable id inside the file */, name, description, colorHex, autoFill: Boolean)`.
  - `FullScreenshot(displayName: String, dateAdded: Long, sizeBytes: Long, ocrText: String, visualLabels: String, isProcessed: Boolean, embeddingB64: String? /* 128 floats, little-endian, Base64 NO_WRAP via java.util.Base64 */, memberships: List<FullMembership>)` and `FullMembership(collectionKey: String, source: String /* AUTO | MANUAL | EXCLUDED */, score: Float?)`.
- Functions: `encodeFullBackup(b: FullBackup): ByteArray` (gzipped), `decodeFullBackup(bytes: ByteArray): Result<FullBackup>` (failure for malformed JSON/gzip or `version > 1`; ignore unknown keys; fail with a clear message "That file isn't a Sift backup"), `embeddingToBase64(FloatArray): String` and `embeddingFromBase64(String): FloatArray?` (null unless exactly 128 finite floats), and `fun restoreMatches(refs: List<RefKey(displayName,dateAdded,sizeBytes)>, candidates: List<Candidate(id, displayName, dateAdded, sizeBytes)>): List<Long?>` — for each backup screenshot the id of the matching current screenshot (exact triple; if several candidates have the same triple, hand them out in order so duplicates map one-to-one; no match -> null).
- Tests `app/src/test/java/com/peexr/sift/data/backup/FullBackupTest.kt`: round-trip (incl. gzip and plain), embedding base64 round trip + rejects wrong length/NaN, malformed/newer version, unknown keys ignored, `restoreMatches` (exact, missing, duplicates one-to-one).

### 2. Repository (IO; dispatchers as appropriate)
- `suspend fun createFullBackup(appVersion: String, settings: BackupSettings): ByteArray`: read screenshots, collections and memberships with a SMALL number of queries (no per-row queries; add DAO queries such as `getAllForBackup()` returning a query-result class with only the needed columns, and `getAllMemberships()`), build the model, encode. Memory: stream or build in chunks if easy, but ~2,500 screenshots (≈ 3 MB JSON) in memory is acceptable.
- `suspend fun restoreFullBackup(bytes: ByteArray): Result<RestoreSummary>`: decode; load current screenshots' (id, displayName, dateAdded, sizeBytes) lightweight rows; `restoreMatches`; in ONE Room transaction (add a DAO `@Transaction` method or use `database.withTransaction`): for matched screenshots set `ocrText`, `visualLabels`, `isProcessed` and `embedding` ONLY WHEN the current row has no embedding / is not processed (never overwrite newer on-device work); create collections that do not already exist by case-insensitive name (reuse the existing collection when the name matches), and upsert memberships for matched screenshots with the saved `source`/`score` (never downgrade an existing MANUAL/EXCLUDED to AUTO). Return `RestoreSummary(screenshotsMatched, screenshotsUnmatched, embeddingsRestored, collectionsCreated, collectionsReused, membershipsApplied)`. Do not trigger auto-fill or indexing inside the restore; the caller does (below). FTS must stay consistent: verify whether the FTS5 table is kept in sync by triggers on UPDATE (it is, if `updatePerception` already works that way) — use the same update path/triggers and say in your summary how you verified it.
- Settings restore is applied by the ViewModel (not the repository): set `autoFillSensitivity`, `indexingQuality`, `autoIndexNewScreenshots`, and `measuredSecPerImageAt280` only if the device has none yet (a measurement from another device must not override this device's own).
